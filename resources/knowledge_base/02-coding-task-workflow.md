# 代码任务处理流程

## 第一步：明确目标

先确定用户要的是解释、诊断、修改还是新增功能。解释和诊断默认只读；只有用户明确要求实现、修复或修改时，才进入写入流程。

把目标转换为可验证结果。例如“修复会话删除”应转成：删除一个会话时，它的消息和会话记录处于同一个事务，并且不存在时返回明确结果。

## 第二步：扫描相关范围

优先查看目录、入口文件、调用方、数据结构和已有测试。不要只根据文件名推断实现，也不要在没有读取当前代码的情况下生成覆盖式修改。

推荐顺序：

```text
目录和入口
→ 请求与响应模型
→ API 路由
→ Service 编排
→ Repository 或外部集成
→ 调用方和测试
```

## 第三步：定位根因或最小改动点

修改应落在真正拥有该职责的位置：

- HTTP 参数和响应格式属于 API 与 Schema。
- 一次业务流程属于 Service。
- Agent 决策、状态和工具选择属于 Agent。
- MySQL、Redis、Chroma 和模型 SDK 的调用属于 integrations。
- 文件内容的分块、索引和检索规则属于 project_index。

不要因为一个功能就复制整套分层，也不要顺手重构无关代码。

## 第四步：修改前确认最新内容

项目索引可能过期。实际编辑前必须读取目标文件最新内容，确认目标片段仍然存在。多个文件共同完成一项功能时，应先理解它们的调用关系，再逐一修改。

## 第五步：验证

验证强度与修改风险匹配：

- 文档：检查链接、结构和事实一致性。
- Python：静态编译、类型检查、相关单元测试。
- Vue/TypeScript：类型检查、构建和必要的界面交互验证。
- 数据库：验证 SQL 参数、事务、回滚和用户隔离。
- 跨端协议：同时检查请求方和接收方字段。

## 第六步：报告

结果报告应区分：已修改、已静态验证、已运行验证、未验证和仍存在的风险。不能把编译通过描述成真实服务联调成功，也不能声称执行了未实际调用的工具。
