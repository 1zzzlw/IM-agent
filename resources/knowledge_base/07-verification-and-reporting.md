# 验证与结果报告

## 分层验证

验证应从便宜、确定的检查开始，再进入需要环境的运行验证：

```text
语法和格式检查
→ 类型检查
→ 单元测试
→ 模块集成测试
→ 真实数据库或外部服务测试
→ 前后端端到端验证
```

前一层通过不等于后一层通过。例如 Python `compileall` 只能证明语法可编译，不能证明 MySQL 密码正确；HTTP 请求返回成功不能证明 SSE 流完整结束。

## 变更类型与验证重点

- 数据库事务：检查成功提交、异常回滚和不存在记录的返回值。
- RAG：检查分块结果、索引数量、用户过滤、来源路径和已知问题的召回情况。
- 文件工具：检查相对路径、越界拒绝、失败回传和写入后复读。
- SSE：检查事件顺序、断线、错误事件、完成事件和前端状态收敛。
- UI：检查普通窗口、全屏、侧栏收缩、弹层边界和空数据状态。

## RAG 的最小验收集

不要只凭“看起来搜到了”判断检索有效。准备少量已知答案：每个问题记录期望命中的文件，并计算 Top K 是否包含该文件。至少覆盖容易混淆的相似文件、无答案问题和不同工作区隔离。

## 结果报告格式

报告至少说明：

1. 改了什么以及行为如何变化；
2. 实际执行了哪些验证；
3. 哪些验证因环境或依赖未执行；
4. 是否存在数据迁移、索引重建或兼容性要求；
5. 用户下一步如何复现和检查。

不得将计划中的功能写成已实现，也不得将静态检查写成真实联调成功。
