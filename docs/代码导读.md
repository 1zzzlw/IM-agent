# 代码导读：从一次对话读懂整个项目

> 先给结论：**这个目录结构是规范的 Agent 项目结构，而且比多数教程项目更克制。** 它没有为了"看起来像框架"而抽 `BaseAgent`、插件系统或微服务，而是把 LangGraph 的图、状态、节点、提示词、工具拆开，再用 `services` 和 `integrations` 兜住生命周期与持久化。之前真正难读的是三处模块级细节：仓储之间的循环、跨模块的私有函数、偏长的仓储文件；这次已经拆开并用真实 MySQL 回归验证。

## 一、目录地图

```text
app/
├── api/                  HTTP / SSE 入口：只做参数校验、身份核对、调 service
├── schemas/              请求、模型输出、SSE 事件的契约（Pydantic）
├── services/             用例编排：一轮对话、一次生活推进、一次通话的生命周期
├── agent/                只负责"怎么想"：图、节点、提示词、工具
│   ├── person/           主角色
│   │   ├── coordinator.py    对话图：prepare → decide → retrieval → appraisal → dialogue
│   │   ├── state.py          图内状态与运行时上下文
│   │   ├── appraisal.py      角色评价（四个 Agent 共用）
│   │   ├── dialogue/         对话节点 + 上下文装配 + 系统提示词
│   │   ├── retrieval/        提取 Agent：混合召回 + 记忆工具
│   │   └── memory/           记忆 Agent：整理、反思约束、召回算法
│   ├── event/            随机事件 Agent：事情产生 → 经历 → 影响
│   └── tools/            受控的服务端电脑工具（时钟、列目录、读文本）
├── llm/                  模型创建（create_chat_model）、结构化输出、媒体连接
├── multimodal/           图片/语音的感知与输出适配（扩展项）
├── embedding/            向量化
├── integrations/         外部资源
│   └── database/         MySQL 仓储，按"基础 → 提交 → 消息 → 查询"分层
│       ├── person_store.py          人物快照、经历/观察、任务入队
│       ├── state_commit.py          commit_appraisal：唯一状态提交入口
│       ├── message_store.py         消息原语（经过/消息/视图/事件）
│       ├── message_history.py       可见历史查询
│       ├── message_repository.py    本轮对话生命周期（接收/表达/结束）
│       └── ...                      生活、记忆、任务、朋友圈、通话、管理员
├── core/                 配置、错误、启动、JSON 序列化、感知纯规则
└── system_knowledge/     心理知识加载
```

配套目录：`resources/psychology/`（行为参考）、`tests/`（71 项，27 项需真实 MySQL）、`docs/`（需求/架构/设计/本导读）。

### 每层"该放什么、不该放什么"

| 层 | 该放 | 不该放 |
| --- | --- | --- |
| `api/` | 路由、参数校验、SSE 封装、权限 | SQL、人格判断、长流程 |
| `services/` | 一次用例的顺序、事务边界、任务调度 | 提示词细节、模型 SDK 细节 |
| `agent/` | 图、节点、提示词、工具、评价规则 | 直接改数据库状态、HTTP |
| `llm/` | 建模型、结构化调用、供应方适配 | 决定人物关系或记忆 |
| `integrations/` | 表读写、向量库、缓存 | 心理判断、业务编排 |
| `core/` | 配置、错误、共享纯规则 | 具体业务行为 |

## 二、一次对话的完整调用链

以 `POST /ai-message/sendMessage` 为例，按文件顺序读：

```text
api/ai_message.py            send_message
  └─ services/ai_message_service.py
       prepare_reply
         ├─ message_repository.find_completed_turn   幂等重放：同一条消息不重复生成
         ├─ model_config_service.resolve_model       选模型（ENV / 个人 / 系统默认）
         ├─ llm/factory.create_chat_model            按配置造模型
         └─ message_repository.begin_turn            入库 + 感知 + 历史裁剪 + 领租约
       stream_reply
         ├─ 未察觉 → defer_turn + settle_turn        先保存，60 秒后再判断
         └─ 已读 → 注册本轮 → 跑 dialogue_graph
              coordinator.py
                prepare    person_store.snapshot
                decide     structured(RetrievalDecision)  只决定"要不要查"
                retrieval  memory_tool → retrieval.agent.retrieve
                appraisal  appraisal.appraise → state_commit.commit_appraisal
                dialogue   dialogue.context.dialogue_messages → 模型 → message_repository.append_expression
         └─ SSE message.completed                    已入库的消息逐条推送
  └─ 结束后 enqueue(memory) → background_service → memory.agent.consolidate
```

生活线是另一条独立链路：

```text
task_repository.schedule_lives   按用户窗口入队（到点才建任务）
  → background_service.worker    claim 租约
  → services/life_service        advance_life
  → agent/event/graph            三阶段
  → life_repository.commit_life_event
       ├─ 经过 + 观察 + 关系 + 目标 + 朋友圈
       ├─ 决定是否打断当前对话（取消 dialogue 任务、结束通话）
       └─ 入队 memory
```

## 四、与常见 Agent 项目模板的对照

| 常见模板 | 本项目 | 说明 |
| --- | --- | --- |
| `graph.py` | `person/coordinator.py`、`event/graph.py` | 都是 LangGraph `StateGraph` |
| `state.py` | `person/state.py`、`event/state.py` | `TypedDict` + `context_schema` |
| `nodes/` | `dialogue/agent.py`、`event/nodes.py` | 节点是普通 async 函数 |
| `prompts/` | 每个 Agent 一个 `prompts.py` | 提示词与节点分离 |
| `tools/` | `retrieval/tools.py`、`agent/tools/local.py` | LangChain `@tool` |
| `config.py` | `core/config.py` | pydantic-settings，支持 `.env` 槽位 |
| `api/` | `app/api/` | FastAPI + SSE |

多出来的三层不是"过度设计"，而是这个项目的需求决定的：

- `services/`：一轮对话跨"模型调用 + 多张表写入 + 后台任务"，必须有地方管顺序与收尾。
- `integrations/`：25 张表 + 向量库 + Redis，SQL 需要集中且可审计。
- `schemas/`：模型输出必须被 Pydantic 卡住，否则"模型说它改了什么"就会变成事实。

规模参考：`app/` 约 101 个 Python 文件、7.4k 行；最大的 `message_repository.py` 385 行，其余业务仓储多在 100~300 行。模块级循环导入为 0；函数内导入 30 处，基本都是"重依赖延迟加载"。

## 五、必须记住的 7 个约定

1. **状态版本**：`world.state_version` 是唯一权威版本。提交状态必须带 `baseVersion`，不匹配就重读重评，绝不覆盖。
2. **幂等键**：消息用 `dedupe_key`，状态变化用 `change_key`，评论用 `request_id`。同一件事重试不会产生第二次影响。
3. **租约**：`background_task.lease_owner + lease_until`。进程内取消只是优化，数据库租约才是最终防线。
4. **观察即知情**：人物只能读 `observation`，不能读 `experience` 的全集。未读正文不会因为后台整理而"偷偷知道"。
5. **JSON 信封**：所有 JSON 字段是 `{schemaVersion, data}`；`dump/load/data/envelope/digest` 是统一读写入口。
6. **错误码**：业务失败一律 `ChatError(code, message, status)`；人物沉默不是错误，技术失败也不能伪装成沉默。
7. **命名**：`snapshot/current` 读；`append/record/commit` 写。读函数无副作用，写函数自己校验幂等/版本/租约。

### 依赖方向（已无环）

```text
api / services
  ↑
message_repository · activity_repository · life_repository   ← 编排一个用例
  ↑
task_repository · state_commit · message_history             ← 租约 / 提交 / 查询
  ↑
character_repository · person_store · message_store          ← 基础读写，只依赖 core
  ↑
core（errors / serialization / perception）
```

（箭头指向被依赖方：上层可以 import 下层，下层不 import 上层。）

旧结构里 `person → activity → message → person` 的环已经拆掉：

- `person_repository` 被删除，读模型/经历/入队去 `person_store`，状态提交去 `state_commit`；
- 约定排期 `schedule` 移到 `state_commit._schedule_activity`（它本来就是"提交评价"的一部分）；
- `message_repository` 只保留本轮生命周期，写入原语在 `message_store`，查询在 `message_history`；
- JSON 信封工具上移到 `core/serialization.py`，不再让业务仓储兼任序列化工具。

读代码时按"基础读写 → 提交 → 编排"的顺序走，依赖只会朝下，不会绕回来。

## 六、这次做过的可读性重构（无行为变化）

| 之前 | 现在 | 原因 |
| --- | --- | --- |
| `agent/runtime.py` + `llm/adapter.py` 两层包装，方法名 `create_agent` 却返回模型 | `llm/factory.create_chat_model` | 三层调用只做一件事；名字还会误导"这里会创建 Agent" |
| `services/character_service.py` 只负责拼对话消息 | `agent/person/dialogue/context.py` | 上下文装配属于对话 Agent，不属于 service |
| `_append` / `_observe` / `_arrive` / `_commit_event` / `_start` 等被其他模块导入 | `append_message` / `record_observation` / `arrive_shared_activity` / `commit_life_event` / `start_session` 等 | 跨模块调用的函数不应是"私有"的 |
| `agent/person/perception.py` 被仓储层导入 | `core/perception.py` | 数据层不应反向依赖 Agent 层；它本身是无 IO 的纯规则 |
| `commit_appraisal` 140 行、`append_message` 110 行 | 拆成 `_write_actor_state` / `_write_relationship` / `_write_goals` / `_write_state_change`，以及 `_insert_experience` / `_insert_message` / `_insert_deliveries` / `_publish_message_event` | 主流程只留"顺序"，细节各自命名 |
| `person_repository.py`（467 行）混合读模型、经历、提交、设置 | `person_store.py`（读/经历/入队）、`state_commit.py`（唯一提交入口）、`user_settings_repository.py` | 一个文件只回答一类问题；提交逻辑不再被读函数淹没 |
| `message_repository.py`（648 行）混合原语、查询、本轮生命周期 | `message_store.py`（原语）、`message_history.py`（查询）、`message_repository.py`（385 行，本轮生命周期） | 写入、读取、有效性判定分开，改一处不用翻整份文件 |
| `person → activity → message → person` 的仓储环 | 删除 `person_repository`；`schedule` 内联进 `state_commit`；`person_store`/`message_store` 不依赖业务仓储 | 依赖方向单向，不再需要"为断环而函数内导入" |
| 空的 `retrieval/algorithms/` 包 | 已删除 | 空包只会让读者以为这里还有实现 |
| 50 处函数内导入 | 30 处 | 只保留"重依赖延迟加载" |

验证：默认环境 `python -m unittest discover -s tests` → 71 项通过、27 项需 MySQL 的跳过；`IMAGENT_TEST_MYSQL=1` 跑真实库 → 71 项通过、仅 2 项实时模型测试跳过。`compileall` 与逐模块 import 均通过。

## 七、建议的阅读顺序（四轮，每轮都能停下来做实验）

**第 1 轮：数据与一条消息**
读设计文档第二节的 25 张表 → `message_repository.begin_turn` → `message_store.append_message`。
实验：在测试库里发一条消息，查 `experience / message / message_delivery / observation / client_event` 各多了几行。

**第 2 轮：人物状态**
读 `appraisal.py` → `state_commit.commit_appraisal` → `state_change`。
实验：故意用旧 `baseVersion` 提交，确认得到 `STATE_CHANGED` 而不是覆盖；同一 `change_key` 提交两次，确认只加一版。

**第 3 轮：记忆与检索**
读 `memory/agent.py` → `memory_repository.save_batch` → `retrieval/agent.py`。
实验：把一条记忆置为 `forgotten`，确认它不再被检索，也不再从聊天历史里被"回忆"出来。

**第 4 轮：生活与中断**
读 `task_repository.schedule_lives` → `background_service.execute` → `life_service` → `event/*` → `commit_life_event`。
实验：把生活窗口调到 5 分钟，观察 `life_event` 的 `phase/status` 与对话任务被取消的顺序。

## 八、不建议现在做的事

- 不要拆微服务：四个 Agent 共享同一份人物状态，拆开只会把事务问题变成分布式事务问题。
- 不要引入 ORM：这套设计的价值就在"复合外键 + 版本 + 租约"看得见，ORM 会把它藏起来。
- 不要抽 `BaseAgent`：四个 Agent 的输入输出差别很大，抽象只会多一层要跳转的代码。
- 不要为每个 Agent 建独立向量库：记忆只有一个持有人，按 `owner_actor_id` 过滤就够了。
- 不要再把 `message_store` / `message_history` / `message_repository` 合回一个文件：分开的边界正好对应"写 / 读 / 这一轮是否还有效"。

## 九、下一步可选的改进（不影响现在学习）

1. `schemas/person.py` 拆成 `public.py` 与 `internal.py`，让"模型输出"和"用户请求"在目录上就分开。
2. 给 `background_service.execute` 做一个显式的 handler 表，替代分支式分派。
3. 补一层可观测性：给每次对话/事件任务记录阶段耗时与模型调用次数，便于比较不同模型。
4. 把 `state_commit` 的四个 `_write_*` 提取为可单测的纯函数（输入 proposal，输出 SQL 参数），减少对真实库的依赖。
