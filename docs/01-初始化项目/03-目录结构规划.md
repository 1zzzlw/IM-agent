# 目录结构规划

## 1. 当前目录

截至本次初始化梳理，项目主要结构如下：

```text
imAgent/
├─ main.py                         # FastAPI 应用和生命周期入口
├─ config.py                       # 环境变量配置模型
├─ pyproject.toml                  # Python 版本与依赖
├─ .env                            # 本地配置，不应提交
├─ app/
│  ├─ api/
│  │  └─ ai_message.py             # AI 消息接口骨架
│  ├─ agent/
│  │  └─ model_client.py           # 当前模型对象创建函数
│  ├─ domain/entities/
│  │  └─ message.py                # 当前 AI 消息请求模型
│  └─ services/
│     ├─ ai_message_service.py     # 当前对话调用逻辑
│     └─ nacos_service.py          # Nacos 注册与注销
└─ docs/
   └─ 01-初始化项目/               # 初始化架构与路线文档
```

这个结构适合验证服务能否启动、注册和调用模型。当前最明显的问题不是目录太少，而是：

- `message.py` 实际是 HTTP 请求模型，不是领域实体；
- `model_client.py` 负责通用模型对象创建，不属于 Agent 工作流本身；
- Nacos 是外部系统集成，不是业务服务；
- `config.py`、应用生命周期和依赖创建仍散落在项目根目录与 `main.py`。

## 2. 推荐的近期目标结构

近期采用轻量分层即可。目录只在出现真实代码时创建，不一次性生成空文件夹。

```text
imAgent/
├─ main.py                         # 只负责创建并导出 FastAPI 应用
├─ pyproject.toml
├─ uv.lock
├─ .env
├─ .env.example                    # 只放示例值
├─ app/
│  ├─ api/                         # HTTP/SSE 输入输出
│  │  ├─ ai_message.py             # 当前 AI 消息路由
│  │  └─ dependencies.py           # 确有共享依赖时再增加
│  ├─ core/                        # 应用级配置与生命周期
│  │  ├─ config.py                 # 配置加载
│  │  └─ lifespan.py               # 模型、Nacos 等资源的启停
│  ├─ schemas/                     # API 请求、响应与 SSE 事件模型
│  │  └─ message.py
│  ├─ services/                    # 一次业务用例的编排
│  │  └─ ai_message_service.py
│  ├─ llm/                         # 模型配置到模型对象的适配
│  │  └─ model_factory.py
│  ├─ agent/                       # 真正出现工作流后再逐步增加
│  │  ├─ graph.py

│  │  ├─ nodes/

│  ├─ test_model_factory.py
```

当同类文件明显增多时再拆子目录。例如路由达到三四个后，再将 `api/ai_message.py` 演进为 `api/routes/ai_message.py`；测试数量增多后，再划分 `unit/`、`integration/` 和 `contract/`。

## 3. 模型模块如何设计

### 3.1 当前 `create_llm()` 是合理起点

现有 `create_llm()` 已经是一个简单的工厂函数。它把 `ChatOpenAI` 的构造细节从业务服务中抽离，方向是正确的，不需要仅为了使用“工厂模式”立即改成类。

近期可以把它从 `app/agent/model_client.py` 移到 `app/llm/model_factory.py`，并让配置成为显式参数：

```python
from langchain_core.language_models import BaseChatModel
from langchain_openai import ChatOpenAI

from app.core.config import ModelConfig


def create_chat_model(settings: ModelConfig) -> BaseChatModel:
    return ChatOpenAI(
        model=settings.llm_model,
        base_url=settings.llm_base_url,
        api_key=settings.llm_api_key,
    )
```

显式传入配置后，函数不再依赖隐藏的全局 `config`，单元测试也可以直接传入测试配置。

### 3.2 什么时候再使用工厂类

满足以下任一真实需求时，再引入 `ModelFactory` 类：

- 同时存在聊天、视觉、总结等多套模型配置；
- 需要按模型用途或供应商选择不同实现；
- 需要集中缓存、复用或关闭模型客户端；
- 创建过程存在较多共享依赖，单个函数已经难以表达。

工厂只负责“创建哪个模型对象”。超时、重试、限流、用量记录和供应商错误转换属于调用策略；这些需求出现后应单独形成模型网关，不要全部塞进工厂类。

### 3.3 对象生命周期

不要在每次请求中执行 `create_llm()`。应用启动时创建并保存模型对象，通过 FastAPI 依赖传给 `ai_message_service`；应用关闭时统一释放需要关闭的资源。测试时则注入假模型。调用关系保持为：

```text
API -> AIMessageService -> Agent/Chain -> ChatModel
                         ^
应用启动 -> ModelFactory ┘
```

如果当前阶段仍只验证一次模型调用，可以先保留每请求创建，等加入 SSE 前再完成生命周期改造，不必同时重构所有代码。

## 4. 为什么这样分层

### 4.1 `schemas` 先于 `domain`

当前 `AIMessageRequest` 只有接口字段和 Pydantic 校验，应放在 `schemas`。等会话归属、运行状态流转等稳定业务规则真正出现后，再创建 `domain`；不要先为数据类制造一层“领域”目录。

### 4.2 `llm` 与 `agent` 分开

`llm` 解决模型对象如何创建和接入，`agent` 解决模型、工具和状态如何编排。普通聊天服务也可能直接使用模型，因此模型创建不应放在 `agent` 内部。

### 4.3 `agent` 与 `services` 分开

Agent 图负责模型推理与工具路由；应用服务负责身份、会话归属、持久化和事务。这样普通聊天与 Agent 聊天可以复用消息能力，也更容易测试。

### 4.4 暂不建立 `ports` 与完整 `infrastructure`

在只有一个实现时，先将外部系统代码集中到 `integrations`。出现第二种数据库实现、明确的仓储替身，或者业务层已经被具体 SDK 污染时，再提取 `ports` 接口和 `infrastructure` 实现。接口应从真实调用需求中长出来，而不是提前猜测。

## 5. 演进顺序

推荐按以下顺序演进：

1. 将配置和生命周期收进 `core`，将请求模型移到 `schemas`；
2. 将 `model_client.py` 演进为 `llm/model_factory.py`，在应用生命周期中复用模型对象；
3. 将 Nacos 移入 `integrations`，保持 `main.py` 轻量；
4. 接入数据库后增加 `integrations/database`，业务确实需要抽象时再增加仓储接口；
5. 出现多个 Agent 节点后再建立 `agent/nodes`；
6. 不为尚未开发的视频、建模、长期记忆提前创建空模块。

## 6. 命名约定

- Python 包、模块、数据库字段：`snake_case`；
- 类名：`PascalCase`；
- HTTP 路径：第一阶段兼容现有 `/ai-message/*`；
- JSON 字段：需要先确定单一规范，迁移期可使用 Pydantic alias 兼容 camelCase 与 snake_case；
- 时间：服务端统一保存 UTC，接口输出 ISO 8601，前端按本地时区展示；
- ID：跨 JavaScript 传递的雪花 ID 使用字符串，避免超过安全整数范围；
- 枚举：代码中使用字符串枚举，接口文档列出允许值，不使用含义不明的裸数字。

## 7. 配置分组

当前 `.env` 已按双下划线组织 `APP`、`NACOS` 和 `CHAT`。建议继续扩展为：

```text
APP__HOST / APP__PORT / APP__ENV
NACOS__SERVER_ADDR / NACOS__SERVICE_NAME / ...
CHAT__LLM_MODEL / CHAT__LLM_BASE_URL / CHAT__LLM_API_KEY
DATABASE__URL / DATABASE__POOL_SIZE
REDIS__URL
AGENT__MAX_STEPS / AGENT__RUN_TIMEOUT_SECONDS
CODING__WORKSPACE_ROOT / CODING__COMMAND_TIMEOUT_SECONDS
OBSERVABILITY__LOG_LEVEL
```

`.env` 只用于本地运行；仓库中的 `.env.example` 不得包含真实密钥。
