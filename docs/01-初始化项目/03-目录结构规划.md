# imAgent 目录结构规划

## 01. 文档目的

本文用于确定 imAgent 后端后续开发时的目录边界，重点解决以下问题：

1. 普通 HTTP/SSE 接口、业务编排和 Agent 工作流分别放在哪里；
2. 系统知识库与用户项目代码索引如何分开；
3. Chat、Build、Plan 三种模式如何组织；
4. Redis、MySQL、向量数据库和 Electron 客户端分别负责什么；
5. 当前代码如何渐进迁移，而不是一次性创建大量空目录。

本文描述的是目标结构，不代表所有目录和功能均已实现。目录只在出现真实代码时创建。

---

## 02. 目录设计原则

### 2.1 从职责出发，不从设计模式出发

目录的核心职责可以概括为：

> `services` 完成一次业务，`agent` 决定下一步，`project_index` 帮助定位代码，`tools` 操作真实文件，`integrations` 连接外部系统。

当前阶段不引入完整 DDD、Ports and Adapters、事件总线或复杂仓储接口。只有当一个目录中出现多种真实实现，或者业务已经被具体 SDK 污染时，再增加抽象层。

### 2.2 系统知识库和项目代码索引必须分开

两者的来源、生命周期和更新方式完全不同：

| 对比项 | 系统知识库 | 项目代码索引 |
|---|---|---|
| 内容来源 | imAgent 自带的工作流、框架知识和排障经验 | 用户当前选择的项目代码和文档 |
| 更新频率 | 低 | 高，文件修改后立即可能过期 |
| 数据范围 | 跨项目复用 | 按用户和工作区隔离 |
| 主要用途 | 提供开发经验和工程知识 | 定位候选文件、符号和依赖关系 |
| 是否能替代文件读取 | 不能 | 不能 |

因此不再使用一个含义模糊的 `agent/rag` 目录容纳全部检索功能，而是拆分为：

```text
app/system_knowledge/        # 系统知识库运行逻辑
app/project_index/           # 用户项目代码索引
resources/system_knowledge/  # 系统知识库原始文档
```

### 2.3 强制规则不能只放进 RAG

以下内容必须始终生效：

- 工作区路径安全限制；
- 不读取或泄漏密钥；
- 修改前先读取原文件；
- 删除和高风险操作的授权要求；
- 不同运行模式允许调用哪些工具；
- 不得声称执行了未经工具确认的操作。

这些规则应放在固定系统提示中，例如 `agent/prompts/policies.py`。系统知识库只保存较长的工作流、框架规范和排障经验，因为 RAG 不能保证每次都检索到某条内容。

### 2.4 项目索引不能替代 read 工具

项目索引只负责定位可能相关的文件和符号。真正分析或修改文件前，Agent 必须通过文件工具读取客户端磁盘上的最新原文。

```text
混合检索定位候选文件
    ↓
read 读取最新原文
    ↓
分析并生成修改方案
    ↓
edit/write 修改
    ↓
重新读取或运行验证
    ↓
将受影响文件的索引标记为过期并增量更新
```

## 05. 各层职责与依赖方向

### 5.1 `api`

只负责接收 HTTP 参数、调用业务服务、转换 HTTP/SSE 响应，以及将业务异常映射为状态码。不负责模型调用、数据库 SQL、Redis Key 拼接或文件工具执行。

### 5.2 `schemas`

保存接口边界的数据结构，包括请求和响应模型、SSE 事件、工具请求与结果、项目索引状态和元数据。

当前 `domain/entities` 中只有字段和校验逻辑的 Pydantic 模型应逐步迁移到这里。只有以后出现包含稳定业务行为和状态变化规则的实体时，再重新评估是否需要 `domain`。

### 5.3 `services`

负责完成一次业务用例，例如保存用户消息、获取会话和工作区、启动 Agent、保存最终回复、协调索引任务以及等待客户端工具结果。

### 5.4 `agent`

负责模型如何决策和调用工具，包括选择 Chat、Build 或 Plan 模式、选择允许使用的工具、维护 Agent State、运行 ReAct 或 Plan-and-Execute，以及根据工具结果决定下一步。

Agent 不直接拼 SQL、Redis Key 或操作用户电脑绝对路径。

### 5.5 `llm`

只负责把模型配置转换成可调用的模型对象，包括供应商适配和模型实例创建。超时、重试、限流和用量统计如果以后变复杂，可以形成模型调用策略，但不全部堆进 Factory。

### 5.6 `system_knowledge`

负责加载和检索 imAgent 自带的稳定知识，不保存用户项目代码。原始文档放在根目录 `resources/system_knowledge`，Python 目录只保存加载、分块、索引和检索逻辑。

### 5.7 `project_index`

负责用户项目的 Repo Map、文件元数据、符号、代码分块、索引状态和混合检索。它只能返回候选文件和代码片段，不能绕开文件工具直接修改客户端文件。

### 5.8 `integrations`

只保存外部系统的具体实现，包括 MySQL、Redis、向量数据库和 Nacos。如果未来确实出现两种数据库或两种向量存储实现，再考虑提取统一接口，不提前创建 `ports`。

推荐依赖方向：

```text
api
 ↓
services
 ├─→ agent
 ├─→ project_index
 ├─→ system_knowledge
 └─→ integrations

agent
 ├─→ llm
 ├─→ project_index
 └─→ tools
```

## 06. 三种 Agent 模式

| 模式 | 主要职责 | 默认文件权限 | 工作流 |
|---|---|---|---|
| Chat | 问答、解释代码、分析问题 | 只读 | 检索 → read → 回答 |
| Build | 直接完成明确的开发任务 | 可读写，高风险操作需授权 | ReAct：判断 → 工具 → 观察 → 继续 |
| Plan | 生成计划并在确认后逐步执行 | 确认前只读，确认后按步骤授权 | Planner → Executor → Replanner |

Plan 模式不应一次生成完整计划后直接不加判断地全部执行，推荐流程为：

```text
Planner 生成 plan[]
    ↓
等待用户确认执行
    ↓
Executor 执行当前步骤或小批次
    ↓
记录工具结果、文件变化和错误
    ↓
Replanner 判断
    ├─ 继续原计划
    ├─ 修改剩余步骤
    ├─ 增加修复步骤
    └─ 完成任务
```

如果第一阶段的“规划”模式只需要输出计划，可以先只实现 `planner.py`。出现真实的逐步执行需求后，再创建 `executor.py`、`replanner.py` 和 `graph.py`。

## 07. 项目代码索引结构

### 7.1 工作区首次注册

当前 imAgent 是远程 Agent 服务，Python 后端无法直接访问用户电脑目录。首次注册工作区时应保持以下边界：

```text
Electron 选择并扫描本地目录
    ↓
Electron 保存：工作区名称 → 绝对根目录
    ↓
Python 接收：用户 ID、工作区名称、相对文件清单
    ↓
建立文件 Manifest 和 Repo Map
    ↓
后台逐步建立符号和向量索引
```

Python、Redis、MySQL 和向量数据库都不应保存用户电脑的绝对根目录。

### 7.2 轻量索引优先

工作区注册后应先建立能够快速完成的轻量索引：

- 相对路径；
- 文件类型和语言；
- 文件大小；
- 内容哈希；
- 修改时间；
- 类名、函数名和接口名；
- import 和依赖关系；
- Git 状态；
- 模块和目录摘要。

轻量索引完成后 Agent 即可通过路径、关键词和符号搜索工作，不需要等待整个项目完成向量化。

### 7.3 代码分块

代码应采用“语义结构优先，长度限制兜底”的方式分块：

1. 文件级摘要用于筛选候选文件；
2. 类、函数、方法、接口等符号作为主要分块边界；
3. 大函数超过限制后，再按逻辑块递归拆分；
4. 每个子块保留文件路径、父级符号和起止行；
5. Markdown 文档按标题层级、段落和完整代码块分块。

### 7.4 混合检索

项目代码不能只依赖向量检索，应逐步支持：

| 检索方式 | 适用场景 |
|---|---|
| 路径检索 | 用户明确提到模块、目录或文件名 |
| 关键词检索 | 错误信息、配置名、方法名 |
| 符号检索 | 类、函数、接口和调用关系 |
| 向量检索 | 用户只描述业务含义，不知道代码名称 |
| 依赖检索 | 查找调用者、实现类和上下游影响 |
| 最近修改检索 | 多步骤任务继续处理刚修改的文件 |

第一版只需支持路径、关键词和符号召回。向量检索完成后再加入混合评分和重排，不需要一开始设计复杂权重学习。

### 7.5 索引状态

文件索引状态建议统一为：

```text
DISCOVERED       已发现文件
METADATA_READY   元数据和符号索引完成
INDEXING         正在建立向量索引
READY            当前版本索引完成
STALE            文件发生变化，索引已过期
FAILED           索引失败
IGNORED          被规则排除
```

文件通过 `write` 或 `edit` 修改成功后，应更新文件哈希，将状态标记为 `STALE`，并优先异步重建该文件索引。即使索引处于 `STALE`，Agent 仍可以通过 `read` 获取最新文件，不应等待向量索引重建。

## 08. 数据存储边界

| 数据 | 建议位置 | 说明 |
|---|---|---|
| 工作区绝对根目录 | Electron 客户端内存或本地安全存储 | 不能上传给远程 Agent |
| 用户、工作区名称和相对文件路径 | MySQL，热点数据可放 Redis | 按用户和工作区隔离 |
| 文件哈希和索引状态 | MySQL 持久化，Redis 缓存 | Redis 清空后仍可恢复 |
| 索引任务和运行状态 | Redis | 适合短期、频繁变化的数据 |
| 代码和文档向量 | 向量数据库 | 系统知识和项目代码使用不同集合 |
| 会话和消息 | MySQL | 长期持久化 |
| 正在等待的 `toolCallId` | 当前内存；多实例后升级 | 多实例需要粘性路由或共享协调机制 |
| API Key | 当前请求或安全的用户级连接配置 | 不写日志、不进入知识库和向量库 |

Redis 适合保存缓存、任务状态和热点 Manifest，但不应被当作所有项目元数据的唯一持久化存储。

## 09. 一次 Vibe Coding 请求的调用链

```text
api/ai_message.py
    ↓
services/ai_message_service.py
    ↓
agent/runtime.py 根据 mode 选择工作流
    ↓
agent/modes/chat.py、build.py 或 plan/graph.py
    ↓
project_index/retriever.py 定位候选文件
    ↓
agent/tools/workspace.py 请求读取最新文件
    ↓
SSE 发送 tool.request
    ↓
Electron 在本地执行 read/edit/write/delete
    ↓
POST workspace/tool/result
    ↓
services/tool_dispatcher.py 唤醒等待中的工具
    ↓
Agent 继续执行并通过 SSE 返回结果
```

在这条链路中：

- `api` 不负责 Agent 决策；
- `services` 不解析代码符号；
- `project_index` 不直接修改文件；
- `agent` 不直接操作 Redis 或 MySQL SDK；
- `integrations` 不决定业务工作流。

## 11. 推荐实施顺序

### 阶段一：保持当前闭环稳定

先确保“发送消息 → SSE 返回 → 模型选择文件工具 → Electron 执行工具 → 工具结果返回后端 → Agent 继续回答”能够稳定运行。此阶段不加入向量库和复杂 Plan 工作流。

### 阶段二：整理基础目录

1. 合并 `core/config.py`；
2. 将接口模型迁移到 `schemas`；
3. 将 `agent/LLM` 迁移到 `llm`；
4. 将 Nacos 收入 `integrations`；
5. 保持 API 路径和外部行为不变。

### 阶段三：Redis 工作区状态

1. 保留 `WorkspaceService` 对外方法；
2. 将内部内存字典逐步替换为 Redis；
3. 保持 Electron 继续持有绝对根目录；
4. 不在业务代码中散落 Redis Key。

### 阶段四：项目轻量索引

1. 建立文件 Manifest；
2. 增加内容哈希和索引状态；
3. 建立 Repo Map；
4. 支持路径、关键词和符号检索；
5. 未完成向量化时仍允许 Agent 工作。

### 阶段五：系统知识库和向量检索

1. 建立系统知识文档清单；
2. 系统知识与项目代码使用不同集合；
3. 为项目文件建立语义分块；
4. 后台增量构建向量索引；
5. 增加混合召回和简单重排。

### 阶段六：Plan 工作流

1. 先实现只生成计划的 Planner；
2. 增加用户确认；
3. 再实现 Executor；
4. 最后加入 Replanner 和可恢复状态。

## 12. 当前不创建的内容

在真实需求出现前，不创建以下复杂结构：

- 多套向量数据库实现；
- 通用 Event Bus；
- Celery 或其他分布式任务系统；
- 完整 DDD 聚合和仓储接口；
- 每种编程语言一个解析器目录；
- 大量没有实现的 Agent Node；
- 为单个实现创建 Factory、Manager、Provider 多层包装；
- 将所有逻辑统一放进一个 `rag`、`common` 或 `utils` 目录。

目录结构的判断标准不是“看起来是否完整”，而是每个目录是否已经具有清晰、真实且互不重复的职责。
