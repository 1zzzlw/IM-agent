# 远程工作区与本地文件工具初版

这篇文档解释当前工作区与文件工具代码为什么这样设计，以及一次完整调用到底经过哪些地方。

先记住一句话：

> Python Agent 负责决定要不要操作文件，Electron 负责真正操作用户电脑上的文件。

Python 服务部署在远程服务器后，不能直接访问用户电脑上的 `E:\AgentProject\imAgent`。因此，后端不能使用本地 `Path.read_text()` 读取这个目录，也不能主动访问 Electron 的 `localhost`。

当前初版使用：

```text
SSE：后端向 Electron 下发工具请求
HTTP：Electron 向后端回传工具结果
```

## 00. 学完这一章应该理解什么

阅读完成后，应当能够回答：

1. 工作区绝对路径保存在哪里？
2. 后端内存保存的是什么？
3. 为什么工作区名称要和用户 ID 一起使用？
4. 模型什么时候会调用 `list/read/write/edit/delete`？
5. 为什么已经有 SSE，还需要 `/tool/result`？
6. 后期 Redis 和 RAG 分别替换哪一部分？

## 01. 真实需求与系统边界

目标流程是：

```text
用户第一次选择工作目录
    ↓
Electron 扫描目录并保存本地根路径
    ↓
后端保存工作区名称和相对文件列表
    ↓
用户带着该工作区继续提问
    ↓
模型自行判断是否需要文件工具
    ↓
需要时选择 list、read 或 write
```

这里有两个不能混淆的世界：

| 位置 | 能访问什么 | 负责什么 |
|---|---|---|
| Electron 主进程 | 用户电脑上的真实磁盘 | 扫描、读取、写入和路径安全校验 |
| Python Agent 服务 | 工作区名称、相对文件列表、模型 | 选择工具、编排调用、等待执行结果 |

远程后端知道 `app/services/workspace_service.py` 这个相对路径就够了，不需要知道用户电脑使用 `E:` 盘还是 `D:` 盘。

## 02. 当前实际有三份内存状态

理解这三份内存，是看懂代码的关键。

### 2.1 Electron 的工作区根目录映射

位置：

```text
WeChat-Electron-vue-vite/src/main/File/fileInfo.js
```

逻辑上可以理解为：

```javascript
workspaceRoots = new Map([
  ['imAgent', 'E:\\AgentProject\\imAgent']
])
```

它保存真实绝对路径，只存在于用户自己的 Electron 进程。

模型和远程后端不应该直接使用这个绝对路径。

### 2.2 Python 的工作区文件集合

位置：

```text
imAgent/app/services/workspace_service.py
```

逻辑上可以理解为：

```python
workspaces = {
    ("user-1001", "imAgent"): {
        "README.md",
        "main.py",
        "app/api/ai_message.py",
    }
}
```

键是：

```text
(user_id, workspace_name)
```

值是相对文件路径集合。

同一个用户再次注册同名工作区时，会覆盖旧集合。不同用户都可以拥有名为 `imAgent` 的工作区，互相不会冲突。

### 2.3 正在等待结果的工具调用

位置：

```text
imAgent/app/services/tool_request_dispatcher.py
```

逻辑上可以理解为：

```python
pending = {
    "tool-abc": Future()
}
```

这不是工作区存储，而是一次工具调用的临时等待表。

例如模型调用 `read_workspace_file()` 后：

1. 后端生成 `toolCallId`；
2. 创建一个等待结果的 `Future`；
3. 向前端发送 `tool.request`；
4. 等待 Electron 返回文件内容；
5. 收到结果后唤醒 `Future`；
6. 删除这一条临时记录。

## 03. 第一次添加工作区发生了什么

入口在：

```text
Ai-chat.vue -> handleAddWorkspace()
```

完整流程：

```text
用户点击“添加本地工作区”
    ↓
Electron 系统目录选择框
    ↓
得到目录名称和绝对路径
    ↓
Electron 主进程扫描文件
    ↓
保存：工作区名称 → 本地绝对根目录
    ↓
将相对文件列表发送给 Python
    ↓
Python 保存：(用户 ID, 工作区名称) → 文件集合
```

### 3.1 为什么发送相对路径

假设用户选择：

```text
E:\AgentProject\imAgent
```

扫描结果发送给后端时是：

```json
[
  "README.md",
  "main.py",
  "app/services/workspace_service.py"
]
```

而不是：

```json
[
  "E:\\AgentProject\\imAgent\\README.md"
]
```

原因有三个：

1. 远程服务器无法使用这个绝对路径；
2. 不向模型泄漏用户电脑的盘符和目录结构；
3. Electron 可以统一用工作区根目录解析相对路径并检查越界。

### 3.2 注册接口

请求：

```http
POST /ai-message/workspace/register
```

示例：

```json
{
  "userId": "user-1001",
  "workspaceName": "imAgent",
  "filePaths": [
    "README.md",
    "main.py",
    "app/api/ai_file.py"
  ]
}
```

响应：

```json
{
  "workspaceName": "imAgent",
  "totalFiles": 3
}
```

## 04. 后续提问时模型如何决定是否调用工具

发送消息时，前端增加：

```json
{
  "content": "帮我看看工作区的消息发送逻辑",
  "workspaceName": "imAgent"
}
```

后端在 `ai_message_service.py` 中先判断有没有工作区名称。

没有工作区：

```python
model = agent_running.submit_agent_task(body.config)
```

这时使用普通聊天模型，不提供文件工具。

选择了工作区：

```python
workspace = workspace_service.get(
    user_id=body.user_id,
    workspace_name=body.workspace_name,
)

agent = agent_running.submit_agent_task(
    body.config,
    tools=build_workspace_tools(workspace),
    system_prompt=...,
)
```

这时模型可以看到五个工具：

```text
list_workspace_files
read_workspace_file
write_workspace_file
edit_workspace_file
delete_workspace_file
```

“可以看到工具”不等于“每次必须调用工具”。

模型会根据用户问题自行判断：

| 用户问题 | 可能行为 |
|---|---|
| “你好” | 不调用工具，直接回答 |
| “有哪些消息相关文件？” | 调用 `list_workspace_files` |
| “读取 ai_message_service.py” | 调用 `read_workspace_file` |
| “把标题改成 XXX” | 先读文件，再调用 `edit_workspace_file` |
| “删除测试文件” | 调用 `delete_workspace_file` |

工具真正传入 LangChain Agent 的位置是：

```text
ai_message_service.py
    ↓ build_workspace_tools(workspace)
agent.py
    ↓ submit_agent_task(config, tools, system_prompt)
agent_creator.py
    ↓ create_langchain_agent(model=llm, tools=tools)
```

因此，排查“模型为什么没有调用工具”时，应依次确认：

1. 前端消息是否携带 `workspaceName`；
2. 后端能否从内存找到该用户的工作区；
3. `build_workspace_tools()` 是否返回五个工具；
4. 当前模型供应商是否支持 Tool Calling；
5. 用户问题是否真的需要访问文件。

## 05. 五个工具分别做什么

### 5.1 `list_workspace_files`

这个工具不访问用户电脑。

它直接遍历 Python 内存中的相对文件集合：

```python
relative_paths = sorted(
    path
    for path in workspace_service.list_files(workspace)
    if not query or query in path
)
```

当前相当于一个简单的文件名搜索：

```text
query = "message"
```

可能返回：

```text
app/api/ai_message.py
app/domain/entities/ai_message.py
app/services/ai_message_service.py
```

这就是“前期遍历内存集合”的实现位置。

### 5.2 `read_workspace_file`

模型传入：

```json
{
  "path": "app/services/ai_message_service.py",
  "startLine": 1,
  "endLine": 200
}
```

Python 本身不读文件，而是创建工具请求并等待 Electron。

### 5.3 `write_workspace_file`

模型传入：

```json
{
  "path": "app/example.py",
  "content": "print('hello')"
}
```

当前初版的 `write` 是完整覆盖写入，适合创建新文件或明确要求整体替换的场景。写入成功后，后端会把新路径加入工作区内存集合。

### 5.4 `edit_workspace_file`

这个工具用于局部文本修改，需要模型提供：

```json
{
  "path": "app/example.py",
  "oldText": "print('old')",
  "newText": "print('new')",
  "replaceAll": false
}
```

默认情况下，`oldText` 必须在文件中只出现一次。出现零次会失败，出现多次会要求模型提供更精确的上下文；只有明确设置 `replaceAll` 才会全部替换。

### 5.5 `delete_workspace_file`

这个工具只处理工作区内的文件，不删除目录。Electron 会把文件移动到系统回收站，而不是直接永久删除。操作成功后，后端会同步移除内存文件集合中的相对路径。系统提示要求模型仅在用户明确要求删除时调用。

## 06. 为什么 `/tool/result` 不能删除

SSE 主要是服务器向客户端发送数据：

```text
Python → Electron
```

但读取文件以后，文件内容需要反向返回：

```text
Electron → Python
```

因此完整读取流程是：

```text
模型调用 read_workspace_file
    ↓
后端生成 toolCallId，并创建 Future
    ↓
SSE 发送 tool.request
    ↓
Electron 主进程读取本地文件
    ↓
POST /ai-message/workspace/tool/result
    ↓
Future 被唤醒，read 工具得到文件内容
    ↓
模型基于文件内容继续回答
```

工具请求事件示例：

```text
event: tool.request
data: {
  "toolCallId": "tool-abc",
  "workspaceName": "imAgent",
  "operation": "read",
  "path": "app/services/ai_message_service.py",
  "startLine": 1,
  "endLine": 200
}
```

结果回传示例：

```json
{
  "toolCallId": "tool-abc",
  "workspaceName": "imAgent",
  "userId": "user-1001",
  "success": true,
  "content": "1: import asyncio\n2: import logging"
}
```

如果删除 `/tool/result`，后端只知道模型想读文件，却永远拿不到文件内容，Agent 也就无法继续这次回答。

未来如果改成 WebSocket，可以不再使用这个 HTTP 接口，但“把工具结果返回给 Agent”的步骤仍然不能消失。

## 07. Electron 如何安全执行本地文件操作

文件操作最终都在：

```text
src/main/File/fileInfo.js
```

Electron 不会直接相信模型传来的路径，而是执行：

```text
工作区名称
    ↓ 查 workspaceRoots
本地绝对根目录
    +
模型提供的相对路径
    ↓ resolve
最终绝对路径
    ↓ 检查仍在根目录内
读写文件
```

下面这些路径应该被拒绝：

```text
../其他目录/secret.txt
C:\Users\xxx\.env
/etc/passwd
通过符号链接跳转到工作区外部的文件
```

当前限制：

| 限制 | 当前值 |
|---|---:|
| 单个工作区扫描文件数 | 100000 |
| 单次读取文件大小 | 1 MB |
| 单次读取行数 | 最多约 1000 行 |
| 单次写入字符数 | 2000000 |
| 工具结果等待时间 | 120 秒 |

扫描时会忽略：

```text
node_modules
.git
out
dist
.idea
.vscode
.venv
```

## 08. 按什么顺序阅读代码

第一次不要从 `tool_request_dispatcher.py` 开始读。推荐顺序：

1. `Ai-chat.vue -> handleAddWorkspace()`：看目录怎样注册；
2. `fileInfo.js -> registerWorkspace()`：看绝对路径和文件扫描保存在哪里；
3. `workspace_service.py -> register()`：看后端怎样保存相对文件集合；
4. `Ai-chat.vue -> handleSubmit()`：看消息怎样携带 `workspaceName`；
5. `ai_message_service.py -> _stream_model_output()`：看普通模型和 Agent 如何分流；
6. `workspace_tools.py -> build_workspace_tools()`：看模型拥有哪些工具；
7. `tool_request_dispatcher.py -> request()/resolve()`：看工具如何等待结果；
8. `AIMessage.js`：看前端如何接收 `tool.request`；
9. `fileInfo.js -> executeWorkspaceTool()`：看本地 read/write；
10. `ai_file.py -> submit_tool_result()`：看结果如何唤醒工具。

## 10. 从内存升级到 Redis

当前业务层调用的是：

```python
workspace_service.register(...)
workspace_service.get(...)
workspace_service.list_files(...)
workspace_service.add_file(...)
```

后期不要让业务代码直接操作 Redis，而是保留这些方法，只替换 `WorkspaceService` 内部实现。

Redis 可以按下面的逻辑组织：

```text
workspace:{userId}:{workspaceName}:meta
workspace:{userId}:{workspaceName}:files
```

例如文件集合可以使用 Redis Set：

```text
SADD workspace:user-1001:imAgent:files README.md
SADD workspace:user-1001:imAgent:files app/api/ai_file.py
```

注意：远程 Redis 仍然不应该保存并尝试执行客户端绝对路径。真正的根目录映射仍属于 Electron 客户端。

如果 Agent 服务部署多个实例，除了工作区集合以外，正在等待的 `toolCallId` 也需要共享状态、消息队列或粘性路由，否则工具请求和结果可能落在不同实例。

## 11. 从内存遍历升级到 RAG

当前 `list_workspace_files(query)` 只是在相对路径集合里做字符串匹配。

后期 RAG 可以增加一个新工具：

```text
search_workspace(query)
```

演进顺序建议是：

```text
第一阶段：遍历内存中的文件名
    ↓
第二阶段：根据文件类型读取并切分文本
    ↓
第三阶段：Embedding + 向量数据库
    ↓
第四阶段：search_workspace 返回相关文件和代码片段
```

向量记录至少需要这些元数据：

```json
{
  "userId": "user-1001",
  "workspaceName": "imAgent",
  "relativePath": "app/services/ai_message_service.py",
  "chunkIndex": 3
}
```

RAG 用来“快速找到可能相关的内容”，但不能替代真实文件工具：

- `search_workspace` 找相关代码；
- `read_workspace_file` 读取磁盘上的最新内容；
- `write_workspace_file` 创建或整体覆盖文件；
- `edit_workspace_file` 精确修改已有文件；
- `delete_workspace_file` 删除明确指定的文件。

## 12. 常见误区

### 误区一：注册了工作区，模型就一定会调用工具

不是。注册工作区只是让工具变得可用，模型仍会根据问题决定是否调用。

### 误区二：`/tool/result` 是另一个多余的聊天接口

不是。它只负责把 Electron 的本地执行结果交给正在等待的工具调用。

### 误区三：后端需要保存用户电脑的绝对路径

不需要。远程后端无法使用该路径，而且会泄漏本地环境信息。

### 误区四：加入 RAG 后不再需要 read

不对。向量索引可能滞后，真正修改前仍应读取磁盘中的最新文件。

### 误区五：工作区名称全局唯一

当前规则是同一用户下唯一，即：

```text
(userId, workspaceName)
```

如果同一用户存在两个同名目录，后注册的目录会覆盖前一个。这是当前初版明确接受的限制。

## 14. 当前初版的限制

当前已经形成代码链路，但仍有这些限制：

1. 工作区和工具等待状态都在进程内存，重启后丢失；
2. 多个 Agent 实例之间不共享工具等待状态；
3. 工作区列表还没有独立查询接口；
4. `write` 是完整覆盖，`edit` 是精确文本替换，目前都没有差异预览和用户审批；
5. 文件变化后不会自动重新扫描；
6. 尚未建立代码分块、Embedding 和 RAG 索引；
7. 不同模型是否稳定支持 Tool Calling，需要实际运行验证；
8. 网关 SSE 超时时间必须大于模型和工具等待时间。

当前阶段先验证最小闭环：

```text
注册工作区
→ 模型选择工具
→ Electron 本地执行
→ 工具结果回传
→ 模型继续回答
```

这个闭环稳定后，再加入 Redis、写入审批、差异预览和 RAG，问题会更容易定位。
