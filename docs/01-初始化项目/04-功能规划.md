# 功能规划

## 1. 总体路线

```mermaid
flowchart LR
    P1[第一阶段\n基础聊天 + Agent + Vibe Coding] --> P2[第二阶段\n视频通话 + 图像识别 + 实时建模]
    P2 --> P3[第三阶段\n全新记忆系统]
```

当前只承诺第一阶段。第二、三阶段用于保留方向，不作为当前架构复杂化的理由。

## 2. 第一阶段一：基础聊天

### 2.1 用户功能

| 功能 | 优先级 | 当前情况 | 第一阶段目标 |
|---|---:|---|---|
| AI 会话入口 | P0 | 前端已有 `type=2` 和 `/aiChat` | 保持接入稳定 |
| 文本消息发送 | P0 | 前后端字段正在对齐 | 请求校验、身份可信 |
| 流式回复 | P0 | 前端有基础 SSE 解析，后端未输出流 | 支持增量、完成、错误事件 |
| 历史消息 | P0 | 前端有调用入口，Python 未实现 | 按会话游标分页加载 |
| 新建会话 | P0 | 前端仅有文字入口/会话体系 | 创建独立 AI 上下文 |
| 停止生成 | P1 | 未实现 | 取消运行并保留已生成内容 |
| 重新生成 | P1 | 未实现 | 基于指定用户消息创建新运行 |
| 删除/归档会话 | P1 | 未形成 AI 闭环 | 默认软删除或归档 |
| Markdown/代码块 | P1 | 当前纯文本显示 | 支持安全渲染与复制 |
| 图片消息 | P2 | 只有选择文件入口 | 留到第二阶段图像识别 |

### 2.2 个性化角色

前端已存在创建、编辑、切换、删除和列表界面。第一阶段应补齐后端，并明确：

- 每个用户只能操作自己的角色；
- 同一用户最多一个激活角色；
- 系统预设角色不可被普通用户修改或删除；
- 删除当前激活角色时回退到默认助手；
- 对话消息记录实际使用的 `personality_id`，便于回放；
- 系统提示词长度和内容需要限制。

## 3. 第一阶段二：Agent 基础能力

基础聊天只生成文本；Agent 能根据任务决定是否调用工具。第一阶段只做一个可控闭环：

```text
接收用户目标
  -> 判断直接回答或调用工具
  -> 校验工具参数
  -> 必要时请求用户确认
  -> 执行工具
  -> 将结果返回模型
  -> 生成最终回答
  -> 保存运行与工具记录
```

### 3.1 最小能力

- 结构化 Agent State；
- 模型节点与工具节点；
- 最大步骤数和总超时；
- 工具白名单；
- 工具输入模型校验；
- 工具执行事件流；
- 取消和失败状态；
- 每次运行可追踪、可审计；
- 失败时给用户可理解的错误，不泄露内部堆栈。

### 3.2 工具风险分级

| 级别 | 例子 | 默认策略 |
|---|---|---|
| 只读 | 列目录、读文件、文本搜索 | 限定工作区后可自动执行 |
| 可恢复写入 | 创建文件、应用补丁 | 先展示计划或差异，再确认 |
| 执行 | 运行测试、构建、格式化 | 命令白名单、超时、输出上限 |
| 高风险 | 删除、覆盖、安装、网络发布 | 第一阶段默认禁止或逐次明确确认 |

## 4. 第一阶段三：Vibe Coding

Vibe Coding 不等同于把一个无限权限终端直接交给模型。推荐先实现“小而完整”的编码任务。

### 4.1 MVP 用户流程

1. 用户选择一个明确的本地工作区；
2. Agent 读取目录与关键文件；
3. Agent 给出简短修改计划；
4. 用户确认需要修改的目标；
5. Agent 生成补丁；
6. 客户端展示文件差异；
7. 用户确认后应用补丁；
8. Agent 运行允许的检查或测试；
9. 返回改动文件、验证结果和遗留问题。

### 4.2 MVP 工具

- `list_files`：列出工作区内文件；
- `read_file`：读取文本文件，限制大小；
- `search_text`：在工作区内搜索；
- `propose_patch`：只生成差异，不立即写入；
- `apply_patch`：审批后应用指定差异；
- `run_command`：仅允许测试、构建、lint 等受控命令；
- `get_git_diff`：展示本次修改。

### 4.3 安全要求

- 工作区根目录由客户端明确选择，服务端解析为绝对路径；
- 拒绝 `..`、符号链接逃逸和工作区外路径；
- 不读取 `.env`、私钥、令牌目录等敏感路径；
- 限制单文件大小、单次输出和命令时长；
- 不拼接执行模型生成的原始 shell 字符串；
- 写入前保存基线或使用 Git diff，保证可回看；
- 每个工具调用保存参数摘要、审批人、结果与耗时；
- 多用户场景下必须隔离工作区，不能依赖一个全局当前目录。

### 4.4 第一阶段不做

- 任意命令执行；
- 自动安装未知依赖；
- 自动提交、推送或部署；
- 跨多个仓库自主修改；
- 长时间无人值守循环；
- 多 Agent 并行改代码。

## 5. 第二阶段方向

### 5.1 视频通话

应优先复用现有 IM 用户关系与在线状态，设计 WebRTC 信令、STUN/TURN、设备权限和通话状态。AI 是否进入通话应作为独立子功能，不与第一阶段 Agent 强绑定。

### 5.2 AI 图像识别

在现有附件上传链路之上增加多模态消息：对象存储保存原图，模型只接收短期授权 URL 或受控字节流，并记录图片与消息的关联。

### 5.3 实时建模

原始路线中的“实时建模输”目前定义不完整。开始前需要先确定它是三维模型生成、屏幕/摄像头理解，还是实时编辑指令输出；三种方向的数据协议和技术栈差异很大。

## 6. 第三阶段：记忆系统

长期记忆应与聊天历史分开设计。建议至少区分：

- 会话上下文：当前会话的最近消息；
- 用户偏好：用户明确允许保存的稳定信息；
- 任务记忆：编码任务的决策、结果和失败原因；
- 知识检索：来自文档或代码库的可追溯片段。

记忆写入需满足“来源可追踪、用户可查看、可更正、可删除、过期可控”。在第一阶段只保留接口边界和数据字段，不提前建设向量库。

## 7. 功能完成定义

一个功能只有同时满足以下条件才标记为“完成”：

- 正常流程可用；
- 越权与非法输入被拒绝；
- 错误能正确结束并反馈；
- 数据可恢复或状态一致；
- 有自动化测试；
- 已通过前端 → 网关 → imAgent 的真实联调。

静态类型检查、模拟模型测试和直接访问 9090 只能算局部验证，不能代替完整链路证明。
