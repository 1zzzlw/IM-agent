## 撰写 `docs/总目标.md`（imAgent 设计方案总纲）

背景：imAgent = FastAPI + LangGraph 的个人编码 Agent，前端为 Electron（`E:\ElectronProject\WeChat-Electron-vue-vite`，Vue3 + Element Plus）。用户要求把 MCP、Skills 等通用 Agent 能力纳入总目标。

调研结论（代码事实）：
- 工具执行位置已隐式二分：`list_workspace_files` 在服务端跑（`app/agent/tools/workspace.py:26`），
  read/write/edit/delete 走 SSE 下发客户端执行再 HTTP 回传（`app/services/tool_dispatcher.py:33`）。
- MCP / Skills 在代码中零痕迹；`project_index/indexer.py` 仅 6 行、`system_knowledge/loader.py` 为空文件（空壳）。

- 真 BUG：`tool.request` 的 `toolCallId` 由 dispatcher 内部生成（`tool_dispatcher.py:43`），

文档确立三条硬决策：
1. 每个工具必须声明 `executor`（server / client / remote），理由：服务端物理上够不到用户磁盘。
2. Skills 是上下文装配（三级渐进披露：索引常驻 → `load_skill` 加载正文 → 按需读 resources），不是工具；
   与 personality 边界划清，只允许一个 system prompt 拼装点。
3. `ToolRegistry` 为唯一工具事实源，命名空间 `tool://` / `mcp://`；加载失败降级不阻断（沿用 WildAgent 红线）。

分期：P0（Registry + 权限闸门 + MCP + Skills + 统一 prompt 装配 + run/step 记录）/ P1（压缩、规则文件、子 Agent、todo、检查点、Hooks）/ P2（RAG、记忆、多模态）。

## 诊断：workspace 注册是进程内内存态（用户提问触发）

结论：
- 注册内容 = 客户端扫描出的**扁平文件相对路径 list**（`schemas/workspace.py:9`），不含目录结构/内容/大小；
  前端 `scanDirectory` 只记录文件，目录仅用于继续遍历（`fileInfo.js:28-30`）；过滤 node_modules/.git 等（`fileInfo.js:6`），上限 10 万。
- 存储 = 进程内 dict 单例（`workspace_service.py:23` + `:110`），无 DB/Redis/落盘。
- 纠正用户"一次性"说法：作用域是**进程**，键 `(user_id, workspace_name)`，与 conversation 无关 → 跨会话存活、跨重启消失、跨实例不共享。

风险分级：
- 🔴 多实例必坏（违反 `02-系统总体架构.md:118` 无状态要求），Nacos lb 轮询下 50% 概率 WorkspaceNotFoundError。
- 🔴 重启后无自动重注册，`workspace_service.py:55` → `ai_message_service.py:200` → run.failed，开发期 reload=True 必踩。
- 🟡 文件清单是注册快照 + 增量猜测，外部编辑器改动不可见；注册覆盖式（`workspace_service.py:48`）会冲掉 add_file 累积。
- 🟡 user_id 来自请求体可伪造（`schemas/workspace.py:7`），违反 `01-项目定位与服务边界.md:39`。

推荐方向（待用户拍板，未落地）：C+A —— 服务端不持工作区状态；root 经 token/请求字段传递；
`list_workspace_files` 改 client executor 实时扫，消灭清单副本这个第二事实源。

## 实测反馈：模型不调工具、直接吐代码 → 提示词补强 + 加分支日志

用户实测（贪吃蛇多文件项目）：导入工作目录后，模型没调用任何工具，直接用文本返回代码。

提示词补了两处（`app/agent/prompts/workspace.py`）：
1. 新增「最重要的一条」：交付物是磁盘文件不是代码块；除非明确说只看代码，不允许用代码块代替
   `write_workspace_file`；收到实现类任务的第一个动作必须是调工具。实测渲染 1791 字符（约 950 token）。
2. 硬约束补：工具调用失败要如实说明，不要假设已写入。

`ai_message_service.py` 加了两条诊断日志（定位"到底走没走 agent 分支"）：
- 无 workspace_name → `logger.warning("...走纯文本分支（无工具、无 system prompt）")`
- 有 workspace_name → `logger.info("AI 运行已挂载 %d 个工具 ...")`

三步定位法（给用户）：
1. 看日志是"未携带 workspace_name"还是"已挂载 7 个工具"。
   ⚠️ 前者说明前端没传，且该分支下 system prompt 也不生效（`runtime.py:29` `if not tools: return llm` 直接返回裸模型）。
2. 已挂载但仍不调工具 → 看 `enableThink`，`_thinking_extra_body` 会塞 `{"thinking":{"type":"enabled"}}`，
   部分 OpenAI 兼容端点在带 tools 时处理 thinking 会忽略工具；先关思考模式重试。
3. 仍不行 → 模型本身 tool calling 支持问题（推理模型/兼容网关常见）。
