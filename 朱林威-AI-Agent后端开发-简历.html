项目难点

  • 集群路由与定向转发：早期用 Redisson 发布订阅做集群间转发，每条消息广播到所有集群，性能随集群数线性放大；改为 Redis 路由表记录用户所在集群，按「集群 ID ↔ 队列 ID」定向投递 MQ，同集群直接转发，离线消息暂存 Redis ZSet 并以雪花 ID 保序；消费端手动 ACK + Redisson 幂等锁去重。
  • 登录态无感刷新：单 Token 在 IM 长待机下频繁掉线；改为 access + refresh 双 Token，refresh 长有效期由网关滑动续期，多端各自维护独立 Token 集合，用户无感刷新。
  • 自定义协议与 Netty 流水线：把编解码、连接管理、路由与业务从单个 Handler 拆成 14 个 Handler；MessageCodecSharable 编解码、MessageDispatcherHandler 策略分发 7 类消息、IdleStateHandler 做 90 秒读空闲心跳；协议为 16 字节固定头 + 变长消息体，用 LengthFieldBasedFrameDecoder 处理 TCP 粘包半包，后续补 Epoll / NIO 自适应。
  • 大文件分片上传：分片原在 Electron 渲染层，切换路由即中断、进度丢失；下沉到主进程，用线程池并发切片，基于文件 MD5 秒传，Redis ZSet 记录已传分片实现断点续传、暂停与失败重传。
  • 高并发与数据一致性：并发登录旧 Token 堆积、抢红包超领、朋友圈热点 Key 同时失效回源；三者同源——多步操作非原子且依赖「先查后写」。红包与并发登录用 Redis Lua 把「幂等判定 + 计数扣减 + 记录写入」压成单脚本；资金侧 MySQL 行锁 + 余额条件更新 + Redis 幂等锁三层校验，转账按 userId 排序加锁防死锁；朋友圈 Cache-Aside + Canal 订阅 binlog 异步失效，随机 TTL + Pipeline 打散过期，唯一索引兜底；用 JMeter 三组场景对比优化前后。
  • imAgent 跨语言架构：划分 Java IM 业务、Python Agent 编排与 Electron 本地执行职责，复用网关鉴权与 Nacos 服务发现；基于 LangChain/LangGraph 与 FastAPI，以 SSE 下发工具请求、HTTP 回传结果，串联代码搜索、diff 预览、文件修改与测试验证；内容哈希防止覆盖人工改动，运行标识、超时与取消管理执行状态，形成可检查的单 Agent 编码闭环。
